> 작성일: 2026-11-12 (v1.2 개정: 2026-11-13)  
> 상태: 개발 착수 — 1단계 설계 확정  
> 개정: v1.2 — 네이버 연동 방식(크롤링 보류 → 업로드·IndexNow), 기술 스택(Spring Boot + React 정적 빌드), 1단계 데이터 모델, 진행 순서 확정  
> 프로젝트명: 미정 (가칭: Marketing Hub) / 작업 폴더: `D:\dev\marketing-hub`

## 1. 프로젝트 개요

### 한 줄 소개
1인 창업가, 인디 개발자, 소규모 기업이 **SNS, 검색엔진, AI 검색, 웹사이트 성과**를 여러 서비스에 각각 접속하지 않고 하나의 플랫폼에서 **관리·분석·실행**할 수 있도록 돕는 셀프서비스 SaaS.

### 출발점
웹사이트를 운영하면서 **Google Search Console, 네이버 서치어드바이저, Bing Webmaster Tools**에 각각 접속해 색인 상태, 검색 성과, URL 및 사이트맵 제출 상태를 확인해야 하는 불편함에서 시작했다.

이 불편을 해결하는 검색엔진 통합 관리에서 출발해, 실제 서비스 홍보에 필요한 SNS, AEO·GEO, 웹사이트 전환 분석까지 연결한다.

### 핵심 원칙
- **제품의 중심은 통합 관리 및 통합 분석**이다. 장기 비전은 SNS·SEO·AEO/GEO·전환 분석을 함께 다루는 것이지만, 첫 출시에서 모든 기능을 구현하지는 않는다.
- SNS 게시·예약도 필요 기능이다. 다만 그것만을 주력 제품으로 만들지는 않는다.
- 여러 도구의 통계 화면을 모으는 데 그치지 않고 **한 번의 작업으로 여러 채널을 관리하고 채널별 결과를 비교**할 수 있어야 한다. 다만 이 통합이 실제 사용자에게 얼마나 가치 있는지는 검증한다.
- 마케팅 전문가가 없는 사람도 스스로 가입하고 연결해 사용할 수 있어야 한다.
- AI는 필수 전제가 아니라 콘텐츠 보조·결과 해석·개선안 제안 등에 선택적으로 활용한다.
- 초기에는 개발자가 직접 자신의 서비스 홍보에 사용하며 기능을 검증한다.
- **약관이 허용하지 않는 수집(로그인 자동화·크롤링)은 하지 않는다.** 허용된 경로가 확보될 때만 자동화한다.

## 2. 타깃 고객과 가치 제안

**타깃**
1. 1인 창업가 및 개인 SaaS 운영자
2. 인디 개발자 / 소규모 개발팀
3. 자체 웹사이트를 운영하는 소규모 기업

**고객의 문제**
- 검색엔진별 관리자 도구를 각각 확인해야 한다.
- SNS 게시 및 예약, SNS 성과 확인도 다른 서비스에서 진행한다.
- AI 검색에서 제품·브랜드가 언급되거나 인용되는지 확인하기 어렵다.
- 검색 노출·SNS 반응·방문·가입·구매 데이터가 분리되어 있어 전체 홍보 성과를 보기 어렵다.
- 여러 개의 유료 도구를 구독하기에는 예산이 부족하다.

**제공 가치**
- 하나의 사이트/제품을 중심으로 채널을 연결한다.
- 검색엔진 관리, SNS 게시·예약, AI 검색 모니터링을 한 곳에서 수행한다.
- 노출과 클릭뿐 아니라 **실제 방문·가입·전환**까지 이어서 분석한다.
- 문제 발생이나 변화에 따른 알림과 후속 조치를 제공한다.

## 3. 주요 기능 범위 (장기)

| 영역 | 통합 관리/실행 | 통합 분석/모니터링 |
|---|---|---|
| **SEO** | Google·Naver·Bing 연결, 사이트맵·URL 제출/변경 알림, 색인 점검 및 이력 | 노출·클릭·키워드·색인 상태 비교, 기술 SEO 오류 점검 |
| **AEO / GEO** | 질문형 콘텐츠·구조화 데이터 등 개선 항목 관리 | ChatGPT·Gemini·Perplexity 등 AI 검색 응답에서 제품 언급·출처 인용 관찰 |
| **SNS** | Instagram·Threads 등 콘텐츠 작성, 예약·발행, 게시 이력 관리 | 게시물 반응, 채널별 링크 유입, 전환 비교 |
| **웹사이트 분석** | 목표·이벤트·UTM 캠페인 설정 | 유입 경로, 방문, 회원가입, 구매 등 전환 분석 |
| **통합 대시보드** | 제품별 연결 상태, 작업 목록, 알림, 권한 관리 | 채널 간 추이 비교 및 개선 과제 우선순위 |

> 1단계에서 실제로 구현하는 범위는 6장 참고.

### 사용 시나리오 (장기)
1. 사용자가 제품명·도메인을 등록하고 사이트 소유권을 검증한다.
2. 검색엔진 계정과 SNS 계정을 연결한다.
3. 각 검색엔진의 색인 상태·사이트맵·검색 성과를 한 화면에서 확인한다.
4. Threads·Instagram 등에 직접 작성한 홍보글을 예약·게시한다.
5. 게시물 링크에 UTM 정보를 붙여 방문·가입·구매 전환을 추적한다.
6. AI 검색의 정해진 질문 표본에서 제품 언급·인용 여부를 확인한다.
7. 종합 대시보드에서 어느 채널의 어떤 활동이 효과적이었는지 파악하고 후속 작업을 수행한다.

## 4. 외부 연동과 현실적인 제약

| 연동 대상 | 접근 방식 | 주요 주의점 |
|---|---|---|
| Google Search Console | 공식 API + OAuth (Google 로그인과 함께 권한 수령) | 검색 실적·사이트맵·URL Inspection 지원. **일반 페이지를 Google Indexing API로 임의 색인 요청하는 것은 지원 범위가 아님**. 일부 검색어는 익명 처리되어 검색어별 합계 ≠ 전체 합계. 데이터는 2~3일 늦게 확정 |
| Bing Webmaster Tools | 공식 Webmaster API, **사용자가 발급한 API 키** 입력 | 제공되는 지표와 URL 조회 범위를 실제 API로 재검증. IndexNow와 연계 가능 |
| Naver Search Advisor | **1단계: 리포트 파일 업로드/수동 입력 + IndexNow 제출 + 사이트맵 점검** | 공식 리포트 조회 API 없음. 다른 계정에 열람 권한을 위임하는 기능도 근거를 찾지 못함. 네이버 이용약관은 자동화된 프로그램을 이용한 무단 수집을 금지 → 로그인 자동화·크롤링은 하지 않음 |
| IndexNow | 공식 프로토콜 (네이버·Bing 지원) | 지원 엔진에 URL 변경 사실을 알리는 기능. **제출 성공 ≠ 수집·색인 성공** |
| 네이버 검색 API | 사용하지 않음 | 2026-09-07 시행 특약 개정(보도 기준)으로 "네이버 검색 결과 제공" 목적으로만 이용 가능, 서버 보관 최대 21일 → 색인 모니터링 용도로 부적합 |
| Instagram | Meta 공식 API | 게시·인사이트 범위는 계정 유형, 앱 심사 및 승인 권한에 따라 달라짐 (비즈니스 인증 필요 가능성) |
| Threads | Meta Threads API | 게시·인사이트 등 지원 범위, 권한 및 호출 제한 확인 필요 |
| AI 검색 서비스 | 허용된 공식 API/접근 방식 | 샘플 질문에서의 언급·인용만 관찰. 전체 검색 이용자에게 보이는 '실제 노출률'로 오인하면 안 됨 |
| 방문·전환 | 자체 이벤트 SDK 또는 외부 분석 연동 | 개인정보·동의·쿠키·어트리뷰션 한계 검토 |

**네이버 연동 원칙**
- 1단계 네이버 기능은 **업로드·제출·점검** 범위다. 사용자 네이버 비밀번호는 받지 않는다.
- 네이버 데이터는 `수집 출처 = 업로드`로 저장하고, 대시보드에 마지막 업로드 시각을 표시한다.
- 서치어드바이저 고객센터에 자동 조회 허용 여부를 서면으로 문의한다. **허용된 경로가 확보되면** 수집기만 교체해 정기 수집을 추가한다(저장 구조는 그대로).

**비교 데이터 해석 원칙:** 플랫폼별 집계 기준과 데이터 지연이 다를 수 있으므로 날짜·출처·집계 기준을 표시한다. 검색 유입 증가와 특정 SNS 게시물의 인과관계를 근거 없이 단정하지 않는다.

## 5. 차별화 전략

경쟁사의 SNS 예약 발행이나 SEO 분석 기능이 존재한다는 이유로 해당 기능을 빼지 않는다. **여러 채널을 통합했을 때 추가로 얻는 가치**를 차별점으로 삼는다.

- **한국형 검색엔진 통합:** 해외 툴이 다루지 않는 네이버를 포함해 Google·Naver·Bing을 한 화면에서 관리.
- **제품 중심 대시보드:** SNS 계정 중심이 아니라 홍보하려는 웹서비스/브랜드 단위로 통합.
- **통합 운영:** 검색엔진별 사이트맵·URL·색인 확인과 SNS 게시 작업을 하나의 작업 흐름에서 수행.
- **통합 성과:** SNS 반응·검색 실적·AI 검색 표본 관찰·사이트 방문/전환을 한 화면에서 확인.
- **가벼운 온보딩:** 마케팅 인력이 없는 소규모 운영자를 위한 쉬운 연결 과정과 합리적인 요금.
- **실행 가능한 알림:** 단순 수치 변화 외에 어느 URL/게시물을 확인하고 무엇을 조치할지 제시.

### 비교·조사 대상
- 해외 통합형: rankingCoach, Semrush
- SNS 관리: Buffer, Metricool, 국내 MARV, Tintio
- 국내 SEO/GEO: NNT Insights, inblog, ChainShift, 블루닷 인텔리전스

위 업체들은 **경쟁 및 기능 비교 대상**이며, 각 서비스의 최신 지원 범위·가격·고객층은 개발 착수 전 공식 자료로 재확인해야 한다. '국내에 유사한 통합 제품이 없다'는 주장은 아직 검증되지 않았다.

## 6. MVP 범위와 단계별 로드맵

**장기 제품 방향:** SNS·SEO·AEO/GEO·방문/전환을 통합 관리·분석한다. **초기 구현 범위:** 1단계에서 Google·Naver·Bing 검색엔진 통합만 구축하고, SNS·전환·AI 검색은 이후 단계에서 확장한다.

### 0단계 — 사전 확인 (1단계와 병행)
- 서치어드바이저 리포트 **내보내기(다운로드) 기능 유무와 형식** 확인 (검색어별/페이지별 제공 여부 포함)
- 네이버 계정 2개로 같은 사이트 **중복 소유확인 가능 여부** 테스트
- 서치어드바이저 고객센터에 **자동 조회 허용 여부 서면 문의**
- 네이버 이용약관·검색 API 특약 원문 확인
- 1인 창업가·소규모 사이트 운영자 대상 사용 빈도·지불 의사 인터뷰
- Meta(Instagram/Threads) 심사 요건과 AI 검색 모니터링 원가는 후속 단계용으로 사전 조사

### 1단계 — Google·Naver·Bing 검색엔진 통합 MVP
**진행 순서**
1. 네이버 리포트 샘플 확보 및 구조 확인 (공통 데이터 모델 확정용)
2. Google 로그인 + Search Console 연동
3. Bing Webmaster API 연동 (API 키)
4. 네이버 리포트 업로드 수집기 + IndexNow 제출 + 사이트맵 점검
5. 세 검색엔진 통합 대시보드
6. (허용 경로 확보 시) 네이버 정기 수집

**기능**
- 사이트(도메인) 등록, 엔진별 사이트 식별자 연결
- Google·Bing: 일별 합계 / 검색어별 / 페이지별 노출·클릭·평균 순위를 매일 수집
- Naver: 리포트 파일 업로드/수동 입력, IndexNow URL 제출
- 사이트맵 상태: 대시보드에서 API로 실시간 조회 (저장하지 않음)
- 통합 대시보드: 엔진별 비교, 데이터 출처(API/업로드), 마지막 수집 시각, 수집 실패 표시
- Google 일반 페이지 자동 색인 요청을 약속하지 않으며, IndexNow 제출과 실제 색인을 구분

**1단계 미정 항목**
- URL 색인 점검(Google URL Inspection API, 사이트당 일일 호출 제한) 포함 여부
- IndexNow 제출 이력 저장 여부

**1단계에서 제외:** SNS, 방문·전환 추적, AEO/GEO, 네이버 자동 수집(허용 경로 확보 전), 다중 사용자 권한 관리

**1단계 완료 기준:** 본인 사이트로 Google·Bing 자동 수집과 네이버 업로드가 한 대시보드에 표시되고, 각 엔진의 데이터 출처·시점·한계가 화면에 드러난다.

### 2단계 — SNS 운영·성과 통합
- Instagram·Threads 계정 연결 및 게시·예약 발행(권한·심사 확보 전제)
- SNS 게시물 이력, 반응·성과 수집
- UTM 링크 생성, 방문·가입·구매 전환 이벤트 추적 및 SNS 게시물별 비교
- 검색엔진 + SNS 성과의 제품 단위 통합 리포트
- 운영 알림·자동화 규칙 추가

### 3단계 — AEO/GEO 모니터링
- 지정 질문에 대한 AI 검색 응답 표본 수집
- 브랜드 언급 및 출처 링크 인용 여부 관찰
- 기술·콘텐츠 점검 및 개선 작업 추천
- 질문·모델별 검사 비용 및 횟수 제한
- 결과 이력·변화 추이 제공(표본·재현성·측정 한계 명시)

### 4단계 — 고도화
- 다중 사이트/협업 기능과 추가 채널 연결
- 검색엔진별 URL 비교, 오류 알림, 자동 재검사 정교화
- 통합 마케팅 활동별 전환 성과 비교 및 개선 제안
- 원가·사용량 기반 요금제 최적화

> **MVP 성공 기준 가설:** 개발자 본인이 실제 웹사이트의 Google·Naver·Bing 상태를 관리하면서 기존 도구 왕복 시간과 반복 작업이 줄어드는지 확인한다. 네이버가 업로드 방식인 상태에서도 가치가 있는지, 외부 사용자의 지속 사용·지불 의사는 인터뷰로 추가 검증한다.

## 7. 기술 아키텍처 (1단계 확정)

```
[브라우저] ──> Spring Boot (서버 1개)
                ├─ /api/**     REST API
                ├─ 정적 파일   React 빌드 결과 (홍보 페이지는 빌드 시 HTML 생성)
                └─ @Scheduled  매일 검색엔진 데이터 수집
                      ├─> Google Search Console API
                      ├─> Bing Webmaster API
                      └─> PostgreSQL
```

- **백엔드:** Spring Boot, JDK 25 (LTS), Gradle, Spring Security OAuth2 Client, Spring Data JPA
- **프론트엔드:** React Router v8 + TypeScript + Tailwind. `ssr: false` 정적 빌드, 홍보 페이지(랜딩·소개 등)만 `prerender`로 빌드 시 HTML 생성 → 네이버 크롤러의 약한 JS 렌더링에 대응. 대시보드는 SPA
- **DB:** PostgreSQL 17 (로컬은 Docker), 마이그레이션은 Flyway
- **정기 수집:** Spring `@Scheduled`. Redis·메시지 큐는 사용하지 않음 (필요해지면 추가)
- **개발 환경:** Vite 개발 서버(5173)가 `/api`를 Spring(8080)으로 프록시 → CORS 설정 불필요
- **배포:** Spring Boot 하나가 API와 React 빌드 결과를 함께 서빙. 배포 위치는 미정
- **수집 구조:** 엔진별 수집기(Google API / Bing API / Naver 업로드)가 같은 형태의 결과를 반환. 네이버 수집 방식이 바뀌어도 수집기만 교체
- **보안:** 인증정보(Google refresh token, Bing API 키)는 앱에서 AES-GCM 암호화 후 저장. 사용자별 데이터 격리, 연동 해제·데이터 삭제, 로그 내 민감정보 차단. 네이버 비밀번호는 받지 않음

### 1단계 데이터 모델 (`db/schema.sql`)

| 테이블 | 역할 | 핵심 컬럼 |
|---|---|---|
| `users` | Google 로그인 사용자 | google_sub(고유), email, name |
| `credential` | 엔진 인증정보 (사용자 단위) | user_id, engine(GOOGLE/BING), secret_enc |
| `site` | 관리 대상 사이트 | user_id, domain, indexnow_key |
| `connection` | 사이트 × 엔진 연결 | site_id, engine(GOOGLE/BING/NAVER), property(엔진 쪽 사이트 식별자) |
| `search_metric` | 세 엔진 공통 검색 성과 | connection_id, metric_date, query, page, impressions, clicks, position, source(API/UPLOAD), collected_at |
| `collect_run` | 수집·업로드 실행 이력 | connection_id, status, date_from/to, rows_upserted, error |

- 인증정보는 사용자 단위: Google 계정 하나 / Bing 키 하나로 여러 사이트를 조회하므로.
- `search_metric`의 `query`/`page` 빈 문자열 규칙: `('', '')` 일별 합계, `(검색어, '')` 검색어별, `('', 페이지)` 페이지별. 검색어×페이지 조합은 1단계에서 저장하지 않음.
- 일별 합계를 별도 저장: GSC는 익명 검색어를 빼고 주므로 검색어별 합계가 전체보다 작음.
- CTR은 저장하지 않고 계산. 평균 순위는 합산 불가라 엔진 값을 그대로 저장.
- `(connection, 날짜, 검색어, 페이지)` 고유 → 재수집 시 덮어쓰기(upsert).
- 연결 상태·마지막 수집 시각은 `collect_run`에서 계산 (중복 저장 안 함).

## 8. 수익 모델 초안

**기본 구조:** 무료 플랜 + 부담 없는 개인용 유료 플랜.

| 플랜 | 가격 | 제공 가치 예시 |
|---|---|---|
| Free | 무료 | 제품 1개, 제한된 검색엔진 연결·기본 분석·일부 발행 기능 |
| Solo | 저가 월 구독 (가격 미정; 기존 4,900~9,900원은 가설) | 검증된 검색엔진 자동 수집, 통합 비교, 향후 SNS 예약 발행 등 |
| Growth | 상위 저가 요금 또는 사용량 기반 | 다중 제품, GEO 질문 검사, 추가 수집량 |

- 가격과 기능 한도는 **확정되지 않은 가설**이다.
- AI 검색 반복 호출, SNS API, 이벤트 저장 비용에 따라 사용량 제한이 필요하다.
- 월 구독에 부담을 느끼는 고객을 위해 연간 할인·크레딧형 옵션도 검토하되, 지속 비용이 큰 기능에 무제한 평생 요금을 섣불리 제공하지 않는다.
- 유료 전환 이유는 '각 기능의 존재'보다 **통합 운영으로 아끼는 시간과 통합 성과를 바탕으로 내리는 의사결정**이어야 한다.

## 9. 위험 요소와 검증 과제

1. **네이버 자동 수집 불가(1단계 우선 리스크):** 공식 API·권한 위임 기능이 없고 약관상 자동 수집이 금지되어, 1단계 네이버는 업로드 방식이다. 이 상태로도 통합 가치가 있는지 인터뷰로 검증하고, 서면 문의로 허용 경로를 확인한다.
2. **SNS 앱 심사:** 개발 및 상업 서비스 전환 시 Meta 권한 승인이 걸림돌이 될 수 있음.
3. **GEO 측정 한계:** AI 응답은 변동성이 있고 API 결과가 실제 소비자 화면과 다를 수 있음.
4. **광범위한 제품 범위:** 장기 통합 비전은 유지하되 검색엔진 통합 → SNS → AEO/GEO 순으로 기능 확장. 검증 결과에 따라 범위 축소 가능.
5. **기존 무료 서비스와 경쟁:** 통합 편의에 실제 지불 의사가 있는지 검증 필요.
6. **전환 추적:** 정확한 채널 귀속이 어렵고 개인정보 보호 설계가 필요.
7. **유지보수 비용:** 외부 API 정책 변경, 토큰 갱신, 수집 실패, 예약 발행 실패 처리 필요.

## 최종 방향 요약

**무엇을 만드는가?**  
1인 창업가·인디 개발자·소규모 기업을 위한 **SNS, SEO, AEO/GEO, 웹사이트 전환의 통합 관리·분석 플랫폼**.

**왜 만드는가?**  
검색엔진과 SNS, AI 검색, 웹사이트 통계가 제각각이라 운영자가 여러 서비스를 반복해서 확인하고 데이터를 직접 비교해야 하기 때문이다.

**무엇이 핵심인가?**  
개별 도구를 대체하는 데 집착하는 대신, **각 채널을 한곳에서 연결·실행·비교하는 경험**을 제공하는 것.

**어떻게 시작하는가?**  
**1단계에서 Google·Naver·Bing 검색엔진 통합만 구현**한다. Google·Bing은 공식 API로 자동 수집하고, 네이버는 리포트 업로드·IndexNow·사이트맵 점검으로 시작해 허용된 경로가 확보되면 정기 수집을 추가한다. 이후 SNS 운영·성과 통합, AEO/GEO를 단계적으로 확장한다.
